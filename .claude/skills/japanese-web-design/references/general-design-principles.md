# 一般的なデザイン原則（業種を問わない普遍パート）

`principles.md` が日本語特有の文字組み・縦組・AIっぽさ回避を扱うのに対し、このファイルは**言語を問わない一般的なレイアウト・タイポグラフィ・進め方の原則**をまとめたもの。新規にページ全体をレイアウトするとき、または実装後の最終レビュー（`SKILL.md` ステップ7）のときに参照する。常に読み込む必要はない。

## 1. レイアウトの4原則（近接・整列・強弱・反復）

- **近接（Proximity）**：関連する要素は近づけ、無関係な要素とは間隔を空ける。余白そのものが情報のグルーピングになる。
- **整列（Alignment）**：要素は見えない基準線（グリッド）に沿って配置する。左揃えが最も読みやすく、しっかりした印象を与える。中央揃えは短いコピーやフォーマルな場面に限定的に使う。
- **強弱（階層／コントラスト）**：重要な情報ほど大きく・濃く・コントラスト高くし、視線誘導を作る。テキストと背景のコントラストは可読性に直結する（WCAG AA基準を下回らない）。
- **反復**：色・フォント・余白の単位・角丸の半径などを繰り返し使うことで、サイト全体の一貫性と「システムとしてのデザイン」感が生まれる。

## 2. 配色の目安比率

70:25:5 の比率（ベースカラー：メインカラー：アクセントカラー）を出発点にする。

- **70%**：背景・余白など、ページの大部分を占めるベースカラー
- **25%**：ブランドカラー・見出し等のメインカラー
- **5%**：CTAボタンなど、行動を促すアクセントカラー

この比率はあくまで出発点であり、業種データ（`data/industry_tone_moderate.csv` 等）の実測トーン分布と矛盾する場合はデータを優先する。

## 3. タイポグラフィの基本

- サイト全体で使うフォントファミリーは2〜3種類以内に絞る（見出し・本文・ラベル程度の役割分担）。
- 本文の1行の長さは、欧文でおよそ80文字以内、日本語ではそれよりやや短め（目安45〜65字程度）に収める。長すぎる行は視線の移動距離が長くなり読みにくい。
- 行間は本文サイズの1.5〜2倍程度が目安（日本語は欧文より広めが基本。詳細は `principles.md` の「字間・行間」参照）。
- セリフ体（明朝体）はサンセリフ体（ゴシック体）よりもやや広い行間を必要とする傾向がある。
- 見出しで単語やフレーズを一つだけイタリック・太字・別色で強調する、意味なくALL CAPSのラベルを付ける、といった「とりあえずそれっぽくする」処理は、ブリーフが求めていない限り避ける。

## 4. モーションは節度をもって

- ページ全体で「見せ場」となる演出は1箇所（ページロード時の一連の動き、または一つの注目すべきリビール）に絞る。すべてのセクションに fade-and-slide-up を、すべてのカードに hover トランジションを付けるのは「選択」ではなく「デフォルト」である。
- ユーザーの操作（開く・展開する・確定する）に応じたモーションは、何が変化したかを示すので歓迎される。
- `prefers-reduced-motion` を必ず尊重する。

### スクロール連動フェードイン（要素が「フワッと」出てくる演出）の実装

日本語のLP・ブランドサイトでは、セクションや画像がスクロールに合わせて「フワッと」浮かび上がるように現れる演出がよく使われる。基本パターンは「初期状態を`opacity: 0`＋`transform: translateY(オフセット)`にしておき、要素が画面に入ったタイミングで`opacity: 1`＋`translateY(0)`のクラスを付与し、CSSのtransitionでなめらかに変化させる」というもの。JavaScriptの役目は「画面に入ったかどうかの判定とクラスの付け外し」だけで、実際のアニメーションはCSS側の`transition`が担う。

**CSS（基本形）**

```css
.js-reveal {
  opacity: 0;
  transform: translateY(32px);
  transition:
    opacity 0.6s ease,
    transform 0.6s cubic-bezier(0.165, 0.84, 0.44, 1);
}
.js-reveal.is-show {
  opacity: 1;
  transform: translateY(0);
}

/* 複数要素を少しずつ時間差で出す（stagger）場合 */
.js-reveal-group > * {
  transition-delay: calc(var(--reveal-index, 0) * 0.08s);
}

@media (prefers-reduced-motion: reduce) {
  .js-reveal {
    transition: none;
    transform: none;
    opacity: 1; /* motionを抑制したい環境では最初から表示してよい */
  }
}
```

**JS（IntersectionObserverで発火、一度出たら戻さない）**

```javascript
const revealEls = document.querySelectorAll(".js-reveal");
const io = new IntersectionObserver(
  (entries) => {
    entries.forEach((entry) => {
      if (entry.isIntersecting) {
        entry.target.classList.add("is-show");
        io.unobserve(entry.target); // スクロールで往復させて何度も明滅させない
      }
    });
  },
  { root: null, rootMargin: "0px 0px -10% 0px", threshold: 0.1 }
);
revealEls.forEach((el, i) => {
  el.style.setProperty("--reveal-index", i % 6); // staggerする場合
  io.observe(el);
});
```

**数値の目安（FANCLの実装から実測・2026年9月時点）**

実際に「フワッと」出てくる演出で定評のある実装例として、FANCLのLP（https://www.fancl.co.jp/skinpatch/index.html ）のCSSを直接取得して調べたところ、以下のような値が使われていた。

- モーダル出現時のフェード＋スライドアップ：初期状態 `opacity: 0; transform: translateY(80px)`（PC）／`translateY(21.33vw)`（SP） → `transition: transform 0.6s cubic-bezier(0.165, 0.84, 0.44, 1), opacity 0.1s linear` → 表示状態 `opacity: 1; transform: translateY(0)`
- 画像単体のフェードイン（`.fsp_statement_image`）：スライドなし、`opacity: 0 → 1` のみのシンプルな不透明度フェード
- スクロール誘導アイコン（`.fsp_scroll-attention`）：`opacity: 0; transition: opacity 0.3s ease` → `is-show`で`opacity: 1`
- クラスの付け外しは`.is-show`という命名で統一されており、JS側は`IntersectionObserver`（`threshold: 0`、`rootMargin: "0px"`）で交差を検知してクラスを切り替える実装だった（WebGLキャンバスのオートプレイ判定に使用されているものを確認。スクロール連動の演出全般も同じ仕組みに乗っていると見られる）。

上記から、実務での目安としては以下を推奨する。

- **オフセット量**：`translateY(20px〜80px)` 程度。大きすぎると「ズレて見える」、小さすぎると「フワッと感」が出ない。
- **duration**：transform（位置）は`0.5s〜0.8s`程度とやや長め、opacity（不透明度）はそれより短いか同程度。長さを揃えすぎず、transformの方をわずかに長くすると重みが出る。
- **easing**：transformには`cubic-bezier(0.165, 0.84, 0.44, 1)`のような「最初は速く、終わりにかけてゆっくり収束する」イージング（ease-out系）を使うと「フワッと」感が出やすい。直線的な`linear`は避ける。
- **一度きりの発火**：スクロールで要素が出たり消えたりするたびに再アニメーションさせると煩雑な印象になりやすいので、`IntersectionObserver`で最初に交差した時点で`unobserve`し、以後は表示状態を維持するのが無難（ページの主旨上「何度も注目させたい」意図がある場合は除く）。
- **staggerは控えめに**：複数カード・複数行を連続して出す場合、1要素あたり`0.05s〜0.1s`程度の遅延差で十分。差を大きくしすぎるとページの体感速度が遅く感じられる。
- **`prefers-reduced-motion`**：モーション低減を希望する環境では、`transition`を無効化し最初から`opacity: 1`で表示する（動きを見せない代わりに情報は即座に見える状態にする）。

## 5. UIライティングの原則

- 言葉は理解を助けるために存在し、装飾のためではない。
- システムの内部用語ではなく、ユーザーの平易な言葉で名付ける。凝った表現より具体的で読みやすい表現を優先する。
- 能動態を使う。CTAボタンは実際に起きることをそのまま書く（「送信する」ではなく「見積もりを送る」等）。フローの中でアクション名を一貫させる（ボタン「公開する」→トースト「公開しました」）。
- エラー・空状態のメッセージは方向性を示す：何が起きたか・どう直すかを説明する。謝るだけ、曖昧なだけのメッセージにしない。

## 6. 進め方：計画 → レビュー → 実装 → 批評

新規にページやセクションをデザインするときは、以下の4段階を踏む。

1. **計画（トークン化）**：配色（4〜6色の主要な色をhexで）・タイポグラフィ（フォントとその役割）・レイアウト（一文の説明＋簡単なワイヤーフレーム、整列方向を明記）・このデザインを"らしく"する原則、を先に言語化する。
2. **実装前レビュー**：上記の計画を業種データ・ブリーフと照らし合わせ、「陥りやすいAI丸わかりパターン」（`principles.md` 参照）に当てはまっていないか確認する。当てはまっていれば、何をどう変えたかを明示してから実装に進む。
3. **実装**：レスポンシブ対応、キーボードフォーカスの可視化、`prefers-reduced-motion`の尊重、アクセシブルなコントラスト、調和の取れた配色という「品質の下限」を満たしながら実装する。CSSの詳細度が高すぎてセクション単位のpadding/marginが打ち消し合っていないかにも注意する。
4. **批評（最終確認）**：スクリーンショットを撮って実際に見て確認する。以下を必ずチェックする。
   - 見出し・リード文で行末の孤立文字（泣き別れ）が起きていないか（`principles.md` の該当セクション参照）
   - モバイル幅（375px前後）でレイアウトが崩れていないか
   - コントラスト比がWCAG AAを満たしているか
   - 「大胆さを効かせる場所」が1箇所に絞られており、それ以外は静かに保たれているか。最後に、ブリーフに貢献していない装飾を一つ削れないか検討する（引き算の仕上げ）。
